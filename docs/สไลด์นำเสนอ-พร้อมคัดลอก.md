# สคริปต์สไลด์นำเสนอโครงงาน (พร้อมคัดลอก)

**ชื่อโครงงาน:** โมเดลสายพานลำเลียงเพื่อการประเมินประสิทธิภาพเครื่องจักรและแสดงผลแบบเรียลไทม์  
**เวอร์ชันแนะนำ:** 15–18 หน้า / พูด 10–12 นาที  
**วิธีใช้:** คัดลอกหัวข้อและเนื้อหาแต่ละหน้าไปวางใน PowerPoint / Google Slides

## หน้า 1 — ปก

**หัวข้อสไลด์:**
โมเดลสายพานลำเลียงเพื่อการประเมินประสิทธิภาพเครื่องจักรและแสดงผลแบบเรียลไทม์  
(Conveyor Belt Model for Near Real-Time OEE Evaluation)

**เนื้อหาใส่สไลด์:**
- ชื่อผู้จัดทำ / รหัสนักศึกษา
- แผนกวิชาเทคโนโลยีสารสนเทศ วิทยาลัยเทคนิคพัทลุง
- อาจารย์ที่ปรึกษา
- ภาคเรียนที่ 1 ปีการศึกษา 2569

**พูดประมาณ:**
“สวัสดีครับ/ค่ะ วันนี้คณะผู้จัดทำขออนุญาตนำเสนอโครงงานโมเดลสายพานลำเลียงเพื่อประเมินประสิทธิภาพเครื่องจักรด้วยดัชนี OEE แบบใกล้เวลาจริง”

## หน้า 2 — ที่มาและความสำคัญ

**หัวข้อสไลด์:** ที่มาของปัญหา

**ใส่เป็น bullet สั้น:**
- โรงงาน SME ยังจดยอดผลิตและเวลาหยุดเครื่องด้วยมือ
- เกิดความล่าช้าของข้อมูล (Data Latency) และ Human Error
- ระบบเชิงพาณิชย์มีต้นทุนค่อนข้างสูง
- ต้องการต้นแบบ IIoT ราคาประหยัดที่วัดค่า OEE ได้

**พูดประมาณ:**
“ปัญหาหลักคือข้อมูลหน้างานยังพึ่งกระดาษ ทำให้ช้าและคลาดเคลื่อน โครงงานนี้จึงสร้างต้นแบบราคาประหยัดเพื่อติดตาม OEE แบบใกล้เวลาจริง”

## หน้า 3 — วัตถุประสงค์

**หัวข้อสไลด์:** วัตถุประสงค์ของโครงงาน

1. ออกแบบชุดสายพานนับ Total / Good อัตโนมัติ และ Waste ผ่าน Manual QC
2. พัฒนาระบบส่งข้อมูล Near Real-time ผ่าน MQTT ไปยัง Time-Series Database
3. สร้างระบบคำนวณ OEE ด้วย Node-RED และแสดงผลบน Grafana
4. ทดสอบความแม่นยำของระบบ โดยความคลาดเคลื่อนไม่เกิน 5%

---

## หน้า 4 — ขอบเขตโครงงาน

**หัวข้อสไลด์:** ขอบเขตการดำเนินงาน

**ในขอบเขต**
- ฮาร์ดแวร์: ESP32 + IR Sensor 3 จุด + สายพานจำลอง
- ซอฟต์แวร์: HiveMQ Cloud, Node-RED, InfluxDB v2, Grafana
- ทดสอบระบบ 105 ชิ้น (3 รอบ × 35) และเปิดระบบต่อเนื่อง 60 นาที
- ประเมินโดยผู้เชี่ยวชาญ 3–5 ท่าน

**นอกขอบเขต**
- ไม่ใช้ AI QC
- ไม่ทำ Defect Chute อัตโนมัติในเวอร์ชันนี้
- ไม่ใช่ระบบ Production-grade เต็มรูปแบบ

---

## หน้า 5 — แนวคิดออกแบบระบบ (4 Layers)

**หัวข้อสไลด์:** สถาปัตยกรรมระบบแบบ 4 เลเยอร์

1. Edge Node Layer — ESP32 อ่านเซนเซอร์และส่งข้อมูล
2. Communication Layer — MQTT ผ่าน HiveMQ Cloud (TLS พอร์ต 8883)
3. Logic & Processing Layer — Node-RED คำนวณ OEE และ Watchdog
4. Storage & Visualization Layer — InfluxDB + Grafana

**ข้อความเด่น 1 บรรทัด:**
ใช้สถาปัตยกรรมแบบแยกส่วน (Decoupling Architecture) แยกงานนับที่ ESP32 และงานคำนวณที่ Node-RED

---

## หน้า 6 — ทฤษฎี OEE

**หัวข้อสไลด์:** ประสิทธิผลโดยรวมของเครื่องจักร (OEE)

**สูตร:**
OEE = Availability × Performance × Quality

- Availability (A): ความพร้อมใช้งาน
- Performance (P): สมรรถนะการผลิต
- Quality (Q): อัตราคุณภาพ

---

## หน้า 7 — การคำนวณในโครงงานนี้

**หัวข้อสไลด์:** สูตรที่ระบบใช้จริง

| ตัวชี้วัด | การคำนวณในระบบ |
| --- | --- |
| Availability | Running Time / Planned Time × 100 |
| Planned Time | เวลาตั้งแต่ Node-RED เริ่มทำงานจนถึงปัจจุบัน (`now - startTime`) |
| Performance | Total / Expected Output × 100 |
| Ideal Cycle Time | 5 วินาทีต่อชิ้น |
| Quality | Good / Total × 100 |
| Watchdog | ไม่มีชิ้นงานผ่านเกิน 60 วินาที → สถานะ IDLE |

---

## หน้า 8 — ฮาร์ดแวร์และ Manual QC

**หัวข้อสไลด์:** การติดตั้งเซนเซอร์และการคัดของเสีย

| ตำแหน่ง | GPIO | หน้าที่ | วิธีนับ |
| --- | --- | --- | --- |
| ต้นสายพาน | 2 | Total | อัตโนมัติ |
| กึ่งกลางสายพาน | 5 | Waste | Manual QC |
| ปลายสายพาน | 4 | Good | อัตโนมัติ |

**คำอธิบายสำคัญ:**
Manual QC = พนักงานตรวจสอบด้วยสายตา หากเป็นชิ้นงานเสีย จะจับชิ้นงานให้โดนเซนเซอร์กลางเพื่อบันทึก Waste

**แนะนำ:** ใส่รูปสายพานจริงประกอบ

---

## หน้า 9 — การไหลของข้อมูล

**หัวข้อสไลด์:** Data Flow

ชิ้นงาน → IR Sensors → ESP32 → MQTT Topics → Node-RED → InfluxDB → Grafana

**Topics**
- `factory/conveyor/total`
- `factory/conveyor/good`
- `factory/conveyor/waste`

---

## หน้า 10 — Firmware ESP32

**หัวข้อสไลด์:** การทำงานฝั่งฮาร์ดแวร์

- อ่านเซนเซอร์แบบ INPUT_PULLUP
- ตรวจจับ Falling Edge เมื่อมีวัตถุตัดผ่าน
- Debounce 150 มิลลิวินาที ป้องกันนับซ้ำ
- ส่งข้อมูลผ่าน MQTT แบบ TLS (พอร์ต 8883)
- เขียนแบบ Non-blocking ด้วย `millis()` ไม่ใช้ `delay()`

---

## หน้า 11 — Node-RED Logic

**หัวข้อสไลด์:** สมองกลคำนวณ OEE

- Subscribe MQTT ทั้ง 3 topics
- อัปเดตค่าประมาณทุก 1 วินาที
- คำนวณ Availability / Performance / Quality / OEE
- Watchdog 60 วินาที เปลี่ยนสถานะเป็น IDLE
- บันทึกลง InfluxDB bucket `conveyor_oee`

---

## หน้า 12 — Grafana Dashboard

**หัวข้อสไลด์:** หน้าจอแสดงผล

ใส่ภาพ Dashboard จริง พร้อมชี้จุด:
- เกจ OEE / Availability / Performance / Quality
- สถานะเครื่อง RUNNING / IDLE
- ยอด Total / Good / Waste
- กราฟแนวโน้ม
- Refresh ทุก 5 วินาที

---

## หน้า 13 — แผนการทดสอบ

**หัวข้อสไลด์:** การทดสอบระบบ

1. นับ Total ที่ต้นสาย
2. นับ Waste ผ่าน Manual QC ที่กลางสาย
3. นับ Good ที่ปลายสาย
4. ทดสอบ Idle Watchdog (> 60 วินาที)
5. ทดสอบความเสถียรต่อเนื่อง 60 นาที
6. ทดสอบความแม่นยำด้วยชิ้นงาน 105 ชิ้น (3 รอบ × 35)

เกณฑ์ความสำเร็จ: ความคลาดเคลื่อนไม่เกิน 5%

## หน้า 15 — สคริปต์สาธิตสด

**หัวข้อสไลด์:** ลำดับการสาธิต

1. ปล่อยชิ้นงานเข้าต้นสาย → Total เพิ่ม
2. พนักงาน QC จับชิ้นงานเสียให้โดนเซนเซอร์กลาง → Waste เพิ่ม
3. ชิ้นงานดีไหลถึงปลายสาย → Good เพิ่ม
4. รอเกิน 60 วินาที → สถานะเปลี่ยนเป็น IDLE
5. ชี้ค่า OEE บน Grafana Dashboard

## คำถามที่มักโดนถาม + แนวตอบสั้น

**ถาม: ทำไมไม่คำนวณ OEE บน ESP32 เลย?**  
ตอบ: แยกหน้าที่ Edge ให้นับและส่งข้อมูล ส่วน Logic ให้อยู่ที่ Node-RED จะปรับสูตรได้โดยไม่ต้องแฟลชบอร์ดใหม่

**ถาม: Waste นับอย่างไร?**  
ตอบ: ใช้ Manual QC พนักงานตรวจด้วยสายตาแล้วจับชิ้นงานเสียให้โดนเซนเซอร์กลาง (GPIO 5)

**ถาม: Planned Time มาจากไหน?**  
ตอบ: ในโครงงานนี้คือเวลาตั้งแต่ Node-RED เริ่มทำงานจนถึงปัจจุบัน (`now - startTime`)

**ถาม: IDLE คืออะไร?**  
ตอบ: หากไม่มีชิ้นงานผ่านเซนเซอร์เกิน 60 วินาที ระบบจะเปลี่ยนสถานะเป็น IDLE และหยุดสะสม Running Time

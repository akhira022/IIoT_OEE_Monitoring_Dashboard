## 1. Phase A — ระบบสาธิตที่ควบคุมได้

**เป้าหมายรวมของเฟส:** ให้คนอื่น (ไม่ใช่ผู้เขียนโค้ด) กดใช้ระบบเองได้ โดยไม่ต้องแก้ไฟล์ code เลย

### Tech Stack ของเฟสนี้

| ส่วน | เทคโนโลยี | เหตุผล |
| --- | --- | --- |
| UI ควบคุม/ตั้งค่า | Node-RED Dashboard (`node-red-dashboard`) | ใช้ของเดิมที่มีอยู่แล้วในโปรเจค ไม่ต้องเพิ่มภาษาใหม่ |
| หน่วยความจำค่าตั้งค่า | Node-RED **Flow/Global Context** (persist แบบไฟล์ `context.json`) | ค่าตั้งไม่หายเมื่อ Node-RED restart |
| แจ้งเตือน | LINE Notify API หรือ Telegram Bot API | ฟรี ตั้งค่าเร็ว |
| Export ข้อมูล | `node-red-contrib-csv` + `file` node | แปลง JSON → CSV ได้ในตัว ไม่ต้องเขียน parser เอง |
| ทดสอบสูตร OEE | flow ทดสอบแยก + Excel เทียบผล | ไม่ต้องใช้ framework ทดสอบซับซ้อนสำหรับโปรเจคระดับนี้ |

### ขั้นตอนปฏิบัติต่อรายการงาน (แบบละเอียด)

#### A-01 Reset ยอด Total/Good/Waste จาก Dashboard

1. เปิด Node-RED Editor → ลาก node `ui_button` จาก palette (ถ้าไม่มีให้ติดตั้ง `node-red-dashboard` ก่อน — ดูคำสั่งท้ายหัวข้อ)
2. ตั้งชื่อปุ่มว่า "Reset ยอดผลิต" กำหนด group/tab ให้อยู่ในหน้าเดียวกับ gauge OEE เดิม
3. ต่อ output ของปุ่มเข้า function node ใหม่ ชื่อ "Reset Counters" ใส่โค้ด:

```javascript
flow.set("total", 0);
flow.set("good", 0);
flow.set("waste", 0);
flow.set("runningTimeSec", 0);
// ไม่ reset startTime เพราะ plannedTime ยังต้องนับต่อเนื่อง (ดูเอกสารพิเศษ plannedTime)

msg.payload = { total: 0, good: 0, waste: 0, resetAt: Date.now() };
return msg;
```

4. ต่อ output ของ function node กลับไปที่ node แสดงผลตัวเลข/gauge เดิม เพื่อให้ตัวเลขในหน้าจอเปลี่ยนเป็น 0 ทันทีโดยไม่ต้องรอรอบคำนวณถัดไป
5. **ทดสอบ:** กดปุ่ม → เช็คว่า (ก) ตัวเลขบนหน้าจอกลับเป็น 0 (ข) `flow.get("total")` ใน debug node เป็น 0 (ค) รอบคำนวณ OEE ถัดไปไม่ error (ลอง publish MQTT ทดสอบสักตัว)
6. **ข้อควรระวัง:** ถ้ามีการเขียนค่าลง InfluxDB ทุกรอบ ให้เขียน record ใหม่ที่มี tag/field บอกว่า "reset event" แยกจาก data ปกติ เพื่อให้กราฟ Grafana ไม่โชว์เส้นดิ่งลงกะทันหันแบบดูสับสน (ใช้ annotation ของ Grafana แทนได้)

#### A-02 / A-03 ตั้งค่า Ideal Cycle Time / Idle Timeout จาก UI

1. เพิ่ม node `ui_numeric` สองตัว: "Ideal Cycle Time (วินาที)" และ "Idle Timeout (วินาที)"
2. ตั้งค่าเริ่มต้น (default) ให้ตรงกับที่ hardcode ไว้เดิม (5 วินาที/ชิ้น, 60 วินาที) เพื่อไม่ให้ผลลัพธ์เปลี่ยนกะทันหันตอน deploy ครั้งแรก
3. ต่อ output เข้า function node:

```javascript
if (msg.topic === "idealCycleTime") {
    flow.set("idealCycleTime", Number(msg.payload));
}
if (msg.topic === "idleTimeoutSec") {
    flow.set("idleTimeoutMs", Number(msg.payload) * 1000);
}
return null; // ไม่ต้องส่งต่อ ค่าจะถูกอ่านในรอบคำนวณ OEE เอง
```

4. แก้ function node คำนวณ OEE เดิม (ที่มี `let idealCycleTime = 5;` และ `let idleTimeoutMs = 60000;`) เป็น:

```javascript
let idealCycleTime = flow.get("idealCycleTime") || 5;
let idleTimeoutMs = flow.get("idleTimeoutMs") || 60000;
```

5. **ทดสอบ:** เปลี่ยนค่า Ideal Cycle Time เป็น 3 วินาที แล้วดูว่า Performance ที่คำนวณเปลี่ยนตามสูตรจริง (`expectedOutput = runningTimeSec / idealCycleTime`) ลองเทียบมือด้วย Excel 1 เคส

#### A-04 แสดงสถานะเครื่อง + connection

1. เพิ่ม `ui_led` (จาก `node-red-contrib-ui-led` ถ้าไม่มีใน dashboard เวอร์ชันที่ใช้) หรือใช้ `ui_text` ที่เปลี่ยนสี background ตาม state
2. ผูกกับตัวแปร `statusText` ที่มีอยู่แล้วใน flow คำนวณ OEE (ไม่ต้องสร้างตัวแปรใหม่)
3. เพิ่มการตรวจสถานะ MQTT: ใช้ event ของ `mqtt-broker` config node (คลิกขวา broker → มี event `connect`, `close`, `error`) หรือใช้ node `status` (สีเทา/เขียว) ที่ node-red แสดงอัตโนมัติใต้ node MQTT in อยู่แล้ว ผูก webhook แจ้งไปหน้า UI ด้วย `ui_led` อีกตัว

#### A-05 บันทึกเหตุผล Downtime

1. เพิ่ม `ui_dropdown` ชื่อ "สาเหตุที่หยุด" ตัวเลือก: `รอวัตถุดิบ`, `ปรับตั้งเครื่อง`, `เปลี่ยนกะ`, `อื่น ๆ`
2. ใน function node ตรวจ status (จุดที่เปลี่ยนจาก RUNNING → IDLE) ให้ trigger `ui_dropdown` ให้ผู้ใช้เลือกเหตุผลภายใน X วินาที ถ้าไม่เลือกให้บันทึกเป็น "ไม่ระบุ"
3. เขียนลง InfluxDB measurement ใหม่:

```javascript
msg.payload = {
    measurement: "downtime_log",
    fields: { reason: dropdownValue },
    tags: { line: "LINE_01" },
    timestamp: new Date()
};
return msg;
```

4. Query กลับมาดูด้วย Flux ง่าย ๆ: `from(bucket:"conveyor_oee") |> range(start:-7d) |> filter(fn:(r) => r._measurement == "downtime_log")`

#### A-06 แจ้งเตือน LINE/Telegram

1. **LINE Notify:** เข้า https://notify-bot.line.me/ → Login → Generate Token → เลือกกลุ่ม/แชทที่จะรับแจ้งเตือน → คัดลอก Token
2. เก็บ Token ไว้ในไฟล์แยก ไม่ใส่ในโค้ดที่ commit (อ่านผ่าน environment variable หรือ Node-RED credential store `$credentials`)
3. เพิ่ม `http request` node method POST ไปที่ `https://notify-api.line.me/api/notify` header `Authorization: Bearer <TOKEN>` body `message=<ข้อความ>`
4. Trigger จาก function node ที่ตรวจ: (ก) status เปลี่ยนเป็น IDLE ค้างนานกว่า 5 นาที (ข) OEE ต่ำกว่า 60% ติดต่อกัน 3 รอบ
5. **ทดสอบ:** ปิดไม่ให้มีชิ้นงานผ่านเซนเซอร์เกิน 5 นาที แล้วเช็คว่า LINE แจ้งเตือนเข้าจริง

#### A-07 เกณฑ์สีมาตรฐาน OEE

1. ใน `ui_gauge` node property มี field `colors` (array 3 สี) — ตั้งเป็น `["red","yellow","green"]` และกำหนดช่วง (segments) ตามเกณฑ์ (เขียว ≥ 85, เหลือง 60–85, แดง < 60)
2. ถ้าต้องการให้ตัวเลข/กราฟอื่นเปลี่ยนสีตามด้วย ให้เขียน function node แยก class:

```javascript
let oee = msg.payload.oee;
let colorClass = oee >= 85 ? "green" : (oee >= 60 ? "yellow" : "red");
msg.payload = { oee: oee, colorClass: colorClass };
return msg;
```

#### A-08 Export CSV รายวัน

1. ติดตั้ง `node-red-contrib-csv` (แปลง object array ↔ CSV string)
2. สร้าง flow: `inject` (ปุ่ม Export) → function node สร้าง Flux query ดึงข้อมูลวันนี้ → InfluxDB node → `csv` node (mode: object to CSV) → `file` node เขียนเป็น `export_YYYY-MM-DD.csv`
3. ทำปุ่มดาวน์โหลดผ่าน Dashboard: ใช้ `http in`/`http response` คู่กันเป็น endpoint `/download/today.csv` แล้วให้ปุ่มใน UI เป็น link ธรรมดา `<a href="/download/today.csv">ดาวน์โหลด</a>` (ใช้ `ui_template` node ใส่ HTML นี้ได้)

#### A-09 ชุดทดสอบสูตร OEE

1. สร้าง flow แยกชื่อ "Test OEE Formula" ไม่ต่อกับ flow จริง
2. ใช้ `inject` node หลายตัว แต่ละตัวจำลอง input ชุดต่างกัน (total, good, waste, runningTimeSec, totalPlannedTime) ส่งเข้า function node คำนวณ OEE ตัวเดียวกับที่ใช้จริง (คัดลอกโค้ดมา)
3. เทียบผลลัพธ์กับตารางคำนวณมือใน Excel (สร้างสูตรเดียวกันไว้ในสเปรดชีต) — ถ้าค่าตรงกันทุกเคส ถือว่าสูตรถูกต้อง บันทึกตารางนี้ไว้แสดงในเล่มรายงานบทที่ 4

#### A-10 Flowchart Manual QC + คู่มือ 1 หน้า

1. ใช้ draw.io (app.diagrams.net, ฟรี) หรือ Mermaid วาด flowchart: ชิ้นงานเข้า → ผ่าน IR Total → พนักงานตรวจสายตา → (ดี → ไหลต่อไป IR Good) / (เสีย → จับให้โดน IR Waste)
2. สรุปเป็น 1 หน้า PDF ด้วย Canva: หัวข้อ, flowchart, ภาพจริงของจุดเซนเซอร์ 3 จุด, เบอร์ติดต่อ/QR code คู่มือฉบับเต็ม

## 2. Phase B — ระบบใช้งานประจำวัน (Ops-ready)

**เป้าหมายรวมของเฟส:** ใช้ต่อเนื่องได้หลายวันโดยไม่ต้องนั่งเฝ้า มีสิทธิ์ผู้ใช้ มี backup กันข้อมูลหาย

### Tech Stack ของเฟสนี้

| ส่วน | เทคโนโลยี | เหตุผล |
| --- | --- | --- |
| Containerization | Docker + Docker Compose | รัน Node-RED, InfluxDB, Grafana พร้อมกันด้วยคำสั่งเดียว ย้ายเครื่องได้ง่าย |
| Secrets | ไฟล์ `.env` + `env_file` ใน compose | แยกรหัสผ่านออกจากซอร์สโค้ดที่ commit ขึ้น Git |
| Login/Role | Node-RED `adminAuth` + Dashboard groups | ไม่ต้องเขียนระบบ login เองทั้งหมด |
| REST API | Node-RED `http in` / `http response` | ไม่ต้องตั้งเซิร์ฟเวอร์ Express แยก ใช้ Node-RED เป็น API ได้เลย |
| Offline Buffer (ESP32) | `LittleFS` | ESP32 มี flashในตัวพอเก็บข้อมูลชั่วคราวได้ ไม่ต้องเพิ่มฮาร์ดแวร์ |
| Backup | `influx backup` CLI + cron/inject | มีคำสั่งสำเร็จรูปในตัว InfluxDB v2 อยู่แล้ว |
| Audit Log | SQLite ไฟล์เดียว (`node-red-node-sqlite`) | ไม่ต้องตั้งเซิร์ฟเวอร์ฐานข้อมูลเพิ่มสำหรับ log ขนาดเล็ก |

### ขั้นตอนปฏิบัติต่อรายการงาน (เรียงตามลำดับแนะนำ)

#### B-15 เลิกฝัง password ในโค้ด (ทำก่อนอันดับ 1 เพราะเป็นความปลอดภัยพื้นฐาน)

1. ฝั่ง ESP32: สร้างไฟล์ `secrets.h` เก็บค่าจริง แล้วเพิ่ม `secrets.h` ใน `.gitignore`

```cpp
// secrets.h (ไม่ commit ไฟล์นี้)
#define WIFI_SSID "ชื่อ Wi-Fi จริง"
#define WIFI_PASSWORD "รหัส Wi-Fi จริง"
#define MQTT_SERVER "xxxxx.s1.eu.hivemq.cloud"
#define MQTT_USER "ชื่อผู้ใช้ HiveMQ จริง"
#define MQTT_PASSWORD "รหัส HiveMQ จริง"
```

```cpp
// esp32_8.3v.ino
#include "secrets.h"
const char* ssid = WIFI_SSID;

```

#### B-02 / B-03 Offline Buffer + Reconnect (ฝั่ง ESP32)

1. เพิ่มไลบรารี `LittleFS` ใน Arduino IDE (Boards Manager ESP32 มีมาให้แล้ว)
2. ตรวจสถานะ MQTT ทุกรอบ loop แบบ non-blocking:

```cpp
#include <LittleFS.h>

void publishOrBuffer(String topic, String payload) {
    if (client.connected()) {
        client.publish(topic.c_str(), payload.c_str());
    } else {
        File f = LittleFS.open("/buffer.txt", "a");
        if (f) {
            f.println(topic + "|" + payload);
            f.close();
        }
    }
}

void flushBufferIfConnected() {
    if (!client.connected() || !LittleFS.exists("/buffer.txt")) return;
    File f = LittleFS.open("/buffer.txt", "r");
    String remaining = "";
    while (f.available()) {
        String line = f.readStringUntil('\n');
        int sep = line.indexOf('|');
        if (sep > 0) {
            client.publish(line.substring(0, sep).c_str(), line.substring(sep + 1).c_str());
        }
    }
    f.close();
    LittleFS.remove("/buffer.txt"); // ลบไฟล์หลัง flush หมด
}
```

3. เรียก `flushBufferIfConnected()` ในจุดที่ reconnect สำเร็จ (ใน non-blocking reconnect loop เดิมที่ใช้ `millis()`)
4. **ทดสอบ:** ปิด Wi-Fi router ชั่วคราวระหว่างมีชิ้นงานไหลผ่าน แล้วเปิดกลับมา เช็คว่าข้อมูลที่ค้างถูกส่งครบไม่หายไปจาก InfluxDB


#### B-09 / B-11 / B-12 รายงาน PDF / กราฟ Downtime / KPI เพิ่ม

1. เพิ่ม panel ใหม่ใน Grafana: Bar chart จัดกลุ่มตามสาเหตุ downtime (Pareto) — Flux query `group(columns: ["reason"]) |> count()`

#### B-14 Backup InfluxDB อัตโนมัติ

4. **เขียน SLA:** ระบุเวลาตอบสนอง (เช่น ภายใน 4 ชั่วโมงทำการ) และเวลาแก้ไขปัญหา (เช่น ภายใน 1 วันทำการ) ไว้ในเอกสารสัญญาบริการ

## 5. พัฒนาเป็นแอป/จอสัมผัส (Touchscreen HMI) — คำตอบละเอียดสำหรับ C-01/C-02

โจทย์ "อยากพัฒนาให้เป็นแอปหรืออะไรก็ได้ที่ทัชกรีน" ตรงกับงาน **C-01 (ปุ่ม Start/Stop/Reset บนเครื่อง)** และ **C-02 (จอ/LED สถานะหน้างาน)** ในแผนหลัก มี 3 แนวทางที่ทำได้ เรียงจากง่าย/เร็ว/ถูก ไปยากขึ้น

### 5.1 เปรียบเทียบ 3 แนวทาง

| แนวทาง | คำอธิบาย | ความซับซ้อนทางเทคนิค | ของที่ต้องซื้อเพิ่ม |
| --- | --- | --- | --- |
| **ตัวเลือก 1: Kiosk Browser** | เอาจอสัมผัสมาเปิดเว็บ Dashboard ที่มีอยู่แล้ว (Node-RED Dashboard) แบบเต็มจอ | ต่ำที่สุด — ไม่ต้องเขียนโค้ดใหม่เลย ใช้ของเดิมทั้งหมด | จอสัมผัส HDMI + Mini PC/Raspberry Pi (หรือใช้โน้ตบุ๊กเดิมก่อนก็ได้) |
| **ตัวเลือก 2: Mobile/Tablet App** | เขียนแอปแยก (Flutter) เชื่อมผ่าน REST API/MQTT ที่ทำใน Phase B | กลาง — ต้องเรียนภาษา Dart และ widget layout ใหม่ | แท็บเล็ต Android/iOS (ใช้เครื่องที่มีอยู่ได้) |
| **ตัวเลือก 3: Embedded HMI บนตัวเครื่อง** | ต่อจอสัมผัส TFT เล็กเข้ากับ ESP32 ตรง ๆ ใช้ LVGL วาด UI โดยไม่พึ่ง PC/เว็บเลย | สูงที่สุด — ต้องเขียน GUI แบบ embedded และจัดการ memory เอง | จอ TFT touch SPI (เช่น 3.5"–5") + สาย/ตัวต้านทานเพิ่ม |

### 5.2 คำแนะนำ (ระดับ ปวส. + งบจำกัด)

**เริ่มจากตัวเลือกที่ 1 ก่อนเสมอ** เพราะ Dashboard ที่มีอยู่แล้วรองรับการแสดงผลบนจอสัมผัสได้ทันที (ปุ่มกด, gauge, ตัวเลข) แค่เปลี่ยนอุปกรณ์แสดงผลจากโน้ตบุ๊กเป็นจอทัชสกรีนตั้งหน้าเครื่องแบบ kiosk เท่านั้น ไม่ต้องเขียนโค้ดใหม่เลย ถ้าอยากขยับไปแอปมือถือ (ตัวเลือก 2) หรือ HMI ฝังในบอร์ด (ตัวเลือก 3) ให้ทำต่อในเฟสถัดไปเมื่อ Phase B (REST API) เสร็จแล้ว เพราะทั้งสองแบบจะเรียกใช้ API เดียวกัน ไม่ต้องแก้ backend ใหม่

### 5.3 ตัวเลือก 1: Kiosk Browser (แนะนำเริ่มก่อน)

**Tech Stack**
- ฮาร์ดแวร์: Raspberry Pi 4 (หรือ Mini PC/โน้ตบุ๊กเดิม) + จอสัมผัส HDMI ขนาด 7–10 นิ้ว
- ซอฟต์แวร์: Chromium ในโหมด `--kiosk` เปิด URL ของ Node-RED Dashboard
- ไม่ต้องเขียนโค้ดเพิ่ม ใช้ Dashboard ที่มีอยู่แล้วจาก Phase A

**ขั้นตอนปฏิบัติแบบละเอียด**

1. **จัดหาอุปกรณ์:** จอสัมผัส HDMI 7–10 นิ้ว (ควรมีตัวควบคุมสัมผัสผ่าน USB in-the-box ไม่ต้องลงไดรเวอร์เพิ่ม) — เริ่มทดสอบด้วยโน้ตบุ๊ก/PC ที่มีอยู่ต่อจอสัมผัสแทนได้ก่อน ไม่ต้องซื้อ Raspberry Pi ทันทีถ้ายังไม่แน่ใจขนาดจอที่ต้องการ
2. **ติดตั้ง OS บน Raspberry Pi:** ใช้ Raspberry Pi OS (Desktop version) ผ่าน Raspberry Pi Imager
3. **ติดตั้งและทดสอบ Chromium kiosk mode:**

```bash
sudo apt update
sudo apt install -y chromium-browser unclutter
chromium-browser --kiosk --incognito --disable-infobars http://<node-red-ip>:1880/ui
```

4. **ปรับ Node-RED Dashboard ให้เหมาะกับจอสัมผัส:**
   - ขยายปุ่มให้ใหญ่พอสำหรับนิ้วแตะ (ขั้นต่ำ ~48px ตามแนวทาง Touch Target ของ Material Design)
   - ลดความหนาแน่นของ widget ต่อหน้าจอ (ไม่เกิน 4–6 widget ต่อหน้าสำหรับจอ 7 นิ้ว)
   - ใช้ theme สีตัดกันชัด (Dark theme มักดูง่ายกว่าในโรงงานที่มีแสงจ้า)
   - แยกหน้า (tab) ชัดเจน เช่น หน้า "สถานะหลัก" (สถานะเครื่อง + OEE gauge + ปุ่ม Start/Stop/Reset) และหน้า "ตั้งค่า" (Ideal Cycle Time, Idle Timeout) แยกออกไปเพื่อไม่ให้ operator กดผิดปุ่มตั้งค่าโดยไม่ตั้งใจ
5. **ตั้งให้เปิด kiosk mode อัตโนมัติตอนบูต (Raspberry Pi OS):** สร้างไฟล์ `~/.config/autostart/kiosk.desktop`:

```ini
[Desktop Entry]
Type=Application
Name=Kiosk
Exec=chromium-browser --kiosk --incognito --disable-infobars http://<node-red-ip>:1880/ui
X-GNOME-Autostart-enabled=true
```

6. **ปิดหน้าจอ screensaver/sleep** เพื่อไม่ให้จอดับระหว่างสาธิต (แก้ในตั้งค่า Power ของ Raspberry Pi OS หรือใช้คำสั่ง `xset s off; xset -dpms; xset s noblank`)
7. **ทดสอบใช้งานจริงหน้าเครื่อง:** ให้พนักงาน QC หรือคนอื่นที่ไม่คุ้นระบบ กดปุ่ม Reset/Start/Stop จากจอสัมผัสจริงระหว่างสาธิต ดูว่าปุ่มกดง่าย ไม่กดโดนผิดปุ่ม
8. **(ถ้าต้องการต่อยอด)** ย้ายไปตัวเลือก 2 หรือ 3 หลัง Phase B เสร็จ โดยใช้ REST API เดิมเป็นจุดเชื่อมต่อ ไม่ต้องแก้ backend ใหม่

**สิ่งที่ต้องระวัง:** ต้องมีเครือข่าย Wi-Fi/LAN ที่ Raspberry Pi เข้าถึง Node-RED ได้เสมอ (แนะนำให้อยู่ใน network เดียวกัน ไม่ต้องผ่านอินเทอร์เน็ต ลด latency และความเสี่ยงเน็ตหลุด)

### 5.4 ตัวเลือก 2: Mobile/Tablet App

**Tech Stack**
- Framework: Flutter (Dart) — รันได้ทั้ง Android/iOS จากโค้ดเดียว มี Widget ปุ่ม/กราฟสำเร็จรูปเยอะ
- การเชื่อมต่อ: HTTP request ไปยัง REST API (จาก B-07) หรือ MQTT client library ในแอป (เช่น package `mqtt_client`)
- State management: `Provider` หรือ `Riverpod` (เพียงพอสำหรับแอปขนาดนี้ ไม่จำเป็นต้องใช้ตัวซับซ้อนกว่านี้)

**ตัวอย่างโค้ดเรียก REST API แบบง่าย (Flutter)**

```dart
import 'package:http/http.dart' as http;
import 'dart:convert';

class OeeApi {
  final String baseUrl = "http://<node-red-ip>:1880/api/oee";

  Future<Map<String, dynamic>> fetchCurrent() async {
    final response = await http.get(Uri.parse("$baseUrl/current"));
    if (response.statusCode == 200) {
      return json.decode(response.body);
    }
    throw Exception("โหลดข้อมูล OEE ไม่สำเร็จ");
  }
}
```

**ขั้นตอนปฏิบัติแบบย่อ (ทำหลัง Phase B เสร็จเท่านั้น เพราะต้องมี REST API ก่อน)**

1. ติดตั้ง Flutter SDK และ Android Studio (สำหรับ emulator/debug)
2. สร้างโปรเจกต์ใหม่ `flutter create oee_app`
3. ออกแบบหน้าจอหลัก: การ์ดแสดง OEE/A/P/Q, ปุ่ม Start/Stop/Reset ขนาดใหญ่, ตัวเลข Total/Good/Waste
4. เขียนฟังก์ชันเรียก API ทุก 2–5 วินาที (ใช้ `Timer.periodic`) เพื่ออัปเดตหน้าจอแบบ near real-time
5. ทดสอบบน emulator ก่อน แล้วค่อย build APK ไปลงแท็บเล็ตจริง (`flutter build apk`)
6. ติดตั้งแท็บเล็ตในโหมด Kiosk ของ Android เอง (Android มีฟีเจอร์ "Screen Pinning" ในตัว ไม่ต้องลงแอปเพิ่ม)

### 5.5 ตัวเลือก 3: Embedded HMI (LVGL บน ESP32)

**Tech Stack**
- ฮาร์ดแวร์: จอสัมผัส TFT แบบ SPI (เช่น ILI9341 + touch controller อย่าง XPT2046) ต่อกับ ESP32 ตัวเดิมหรือตัวที่ 2 แยกหน้าที่แสดงผล
- ไลบรารี: `LVGL` (Light and Versatile Graphics Library) วาด UI + `TFT_eSPI` ขับจอ
- ต้องออกแบบหน้าจอ (Screen) แยกส่วน: หน้าสถานะ (RUNNING/IDLE), หน้าตัวเลข OEE, หน้าปุ่มควบคุม
- ถ้าใช้ ESP32 แยกจากตัวหลัก (ที่รับเซนเซอร์) ต้องส่งค่าระหว่างกันผ่าน MQTT (subscribe topic เดิม) หรือ Serial/I2C ถ้าอยู่ใกล้กันในกล่องเดียว

**ตัวอย่างโค้ดเริ่มต้น LVGL (แสดงตัวเลข OEE + ปุ่ม Reset)**

```cpp
#include <lvgl.h>
#include <TFT_eSPI.h>

lv_obj_t *label_oee;
lv_obj_t *btn_reset;

void reset_btn_event_cb(lv_event_t *e) {
    if (lv_event_get_code(e) == LV_EVENT_CLICKED) {
        // ส่งคำสั่ง reset ผ่าน MQTT publish ไปยัง topic ที่ ESP32 หลักรออยู่
        client.publish("factory/conveyor/cmd/reset", "1");
    }
}

void setup_ui() {
    label_oee = lv_label_create(lv_scr_act());
    lv_label_set_text(label_oee, "OEE: --%");
    lv_obj_align(label_oee, LV_ALIGN_TOP_MID, 0, 20);

    btn_reset = lv_btn_create(lv_scr_act());
    lv_obj_set_size(btn_reset, 120, 60);
    lv_obj_align(btn_reset, LV_ALIGN_BOTTOM_MID, 0, -20);
    lv_obj_add_event_cb(btn_reset, reset_btn_event_cb, LV_EVENT_CLICKED, NULL);

    lv_obj_t *btn_label = lv_label_create(btn_reset);
    lv_label_set_text(btn_label, "RESET");
}

void update_oee_label(float oee) {
    char buf[32];
    snprintf(buf, sizeof(buf), "OEE: %.1f%%", oee);
    lv_label_set_text(label_oee, buf);
}
```

**ขั้นตอนปฏิบัติแบบย่อ (เฟสยากที่สุด — ทำเป็นลำดับสุดท้ายถ้ามีเวลา)**

1. ต่อจอ TFT SPI เข้ากับ ESP32 ตามผัง pinout ของจอที่เลือก (แต่ละรุ่นผังต่างกัน ต้องดู datasheet ของจอนั้น)
2. ติดตั้งไลบรารี `TFT_eSPI` และตั้งค่าไฟล์ `User_Setup.h` ให้ตรงกับจอที่ใช้
3. ติดตั้งไลบรารี `lvgl` ผ่าน Library Manager แล้ว config `lv_conf.h` ตามคู่มือ LVGL
4. เขียน UI ทีละหน้า เริ่มจากหน้าง่ายที่สุด (ตัวเลข + ปุ่มเดียว) ก่อนค่อยเพิ่มหน้าอื่น
5. ทดสอบการสัมผัส (touch calibration) — จอ SPI ทั่วไปต้อง calibrate ตำแหน่งสัมผัสให้ตรงกับพิกัดจอก่อนใช้งานจริง
6. เชื่อม MQTT/Serial ระหว่างจอกับ ESP32 หลัก แล้วทดสอบ end-to-end

### 5.6 สรุปสิ่งที่ต้องเพิ่มในแผนเฟส C (อัปเดตอ้างอิง)

งาน C-01/C-02 ในเอกสารแผนหลักควรตีความว่า "เริ่มจาก Kiosk Browser บนจอสัมผัส" เป็นค่าเริ่มต้น (Definition of Done ของ C-01/C-02 = มีจอสัมผัสหน้าเครื่องที่กดควบคุม Start/Stop/Reset ได้จริงโดยไม่ต้องใช้โน้ตบุ๊ก) ส่วนแอปมือถือ (ตัวเลือก 2) หรือ Embedded HMI (ตัวเลือก 3) ให้เก็บไว้เป็นตัวเลือกเสริมถ้ามีเวลาและอยากฝึกเพิ่มในภายหลัง ไม่จำเป็นต้องทำทั้ง 3 แบบ

## 6. คำถามที่พบบ่อย (FAQ)

**ถาม: ต้องซื้อ Raspberry Pi ก่อนเริ่มทำจอสัมผัสไหม?**  
ตอบ: ไม่จำเป็น เริ่มทดสอบด้วยโน้ตบุ๊ก/PC ที่มีอยู่ต่อจอสัมผัส HDMI ก่อนได้ ถ้าพอใจกับผลลัพธ์แล้วค่อยซื้อ Raspberry Pi หรือ Mini PC มาติดตั้งประจำที่ทีหลัง เพื่อไม่ต้องแบกโน้ตบุ๊กไปด้วยตลอด

**ถาม: จอสัมผัสที่ซื้อมาต้องรองรับ multi-touch ไหม?**  
ตอบ: ไม่จำเป็นสำหรับ Dashboard ควบคุมง่าย ๆ (กดปุ่มทีละจุด) จอแบบ single-touch (resistive หรือ capacitive ทั่วไป) เพียงพอแล้ว multi-touch จำเป็นเฉพาะถ้าจะทำ gesture ซับซ้อน เช่น pinch-to-zoom บนกราฟ

**ถาม: ถ้าอยากทำแอป Android ต้องรู้ภาษาโปรแกรมอะไรก่อน?**  
ตอบ: แนะนำ Dart (สำหรับ Flutter) ซึ่งไวยากรณ์คล้าย Java/JavaScript เรียนรู้ได้เร็วถ้ามีพื้นฐาน C/C++ จากการเขียน ESP32 อยู่แล้ว ไม่จำเป็นต้องรู้ Kotlin/Java ของ Android โดยตรงถ้าใช้ Flutter

**ถาม: ถ้าไม่มีงบสั่งผลิต PCB ทำอย่างไรได้บ้าง?**  
ตอบ: ใช้ Prototype Board (แผ่นปรินท์วงจรเปล่าที่บัดกรีสายเอง) แทนไปก่อนในรอบสาธิตแรก ค่อยสั่งผลิต PCB จริงตอนใกล้ส่งมอบลูกค้าจริงหรือมีงบเพิ่ม เพราะ PCB มีค่าใช้จ่ายขั้นต่ำต่อรอบสั่งผลิต

**ถาม: Docker จำเป็นแค่ไหน ถ้ายังรันบนเครื่องเดียวอยู่?**  
ตอบ: ถ้าเป็นแค่เครื่องสาธิตเครื่องเดียวที่ไม่ย้ายที่ ยังไม่จำเป็นเร่งด่วน แต่แนะนำให้ทำตั้งแต่ Phase B เพราะพอถึงเวลาส่งมอบลูกค้าจริง (Phase C) การมี Docker Compose จะทำให้ "ติดตั้งซ้ำได้จากเอกสาร" ง่ายกว่ามาก ไม่ต้องมานั่งลงโปรแกรมทีละตัวหน้าเครื่องลูกค้า

**ถาม: LINE Notify ยังใช้ได้อยู่ไหม (เคยมีข่าวว่าจะปิดบริการ)?**  
ตอบ: ควรตรวจสอบสถานะบริการ LINE Notify ล่าสุดก่อนเริ่มทำ A-06 เพราะผู้ให้บริการอาจเปลี่ยนแปลงเงื่อนไข/ยกเลิกบริการได้ ถ้าใช้ไม่ได้แล้วให้สลับไปใช้ Telegram Bot API แทน (ฟรีเหมือนกัน ขั้นตอนใกล้เคียงกัน) โค้ดในเอกสารนี้ปรับเปลี่ยน endpoint เป็น Telegram ได้โดยไม่ต้องเปลี่ยนโครงสร้าง flow

**ถาม: เลือกทำ Manual QC ต่อไป หรือควรรีบทำ Defect Chute อัตโนมัติ (C-04)?**  
ตอบ: ไม่ต้องรีบทำ Defect Chute เพราะ Manual QC เป็นจุดขายของโปรเจคระดับ ปวส. อยู่แล้ว (แสดงการผสานคนกับระบบอัตโนมัติ) ให้ทำ Defect Chute เป็นทางเลือกอัปเกรดขั้นสูงตอนใกล้ Phase C-D ถ้าต้องการลดการพึ่งพาพนักงานจริง ๆ

**มีคำถามอื่นเพิ่มเติม?** ถามได้เรื่อย ๆ ระหว่างลงมือทำแต่ละเฟส เอกสารนี้ปรับปรุงเพิ่มเนื้อหาใหม่ตามคำถามที่เกิดขึ้นจริงได้ตลอด ไม่ต้องรอทำเสร็จทั้งหมดก่อนถาม
